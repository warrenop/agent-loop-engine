# Session 优化分析(本引擎的证据基础)

数据来源:自建工具「Cursor Context Usage」(`http://192.168.3.131:4173/`)导出的 6 个真实开发 session。

## 一、6 个 session 是同一套工作流

| Session | 名称 | 总 token | 占满 |
|---|---|---|---|
| d621045a | 需求分析与计划制定 | 130K | 65% |
| b9d3a890 | 需求分析与计划制定 #2 | 129K | 64% |
| f5166e62 | 处方库关联商品(跨端调研) | 114K | 57% |
| 91757c58 | 定时任务报警信息修改 | 83K | 41% |
| 99140734 | 舌诊 PK 报告缺门店 ID(bug) | 77K | 38% |
| 6741e548 | 分析需求 URL→提问→计划→实现 | 42K | 21% |

共同骨架:**录入需求(常来自 dillonz.com 原型 URL)→ 澄清提问 → 调研代码 → 计划 → 实现 → 验证**。这就是提炼成 Agent Loop 的依据。

## 二、最大浪费:探索类调用占 50–82%

| Session | 总工具调用 | 探索(Read/Grep/Glob/语义)占比 | conversation token |
|---|---|---|---|
| 需求分析#1 | 140 | **68%**(Read 53, Grep 36) | 96K |
| 舌诊 bug | 45 | **82%**(Read 23, Grep 13) | 41K |
| 需求分析#2 | 163 | 60%(Read 51, Grep 37) | 93K |
| 处方库跨端 | 75 | 73%(Grep 29, Read 24) | 78K |
| 定时任务 | 55 | 52%(Grep 15, Read 12) | 47K |
| 需求URL | 14 | 50% | 12K |

- Read/Grep 在每个 session 都是头号调用,且**散乱、反复**;每条结果永久驻留对话。
- `conversation` 区(41K–96K)是单 session 总开销的 ~74%,是绝对大头。

→ **对策**:INVESTIGATE 阶段「先定位后精读、同一文件不重读、发现落盘 context-map、设探索预算」(护栏 G1/G2/G3/G6)。

## 三、固定开销每 session ~34K

| 类别 | token | 说明 |
|---|---|---|
| Rules | ~11.6K | 常驻规则(含 CLAUDE.md ~4.7K) |
| Skills | ~10K | **99 个条目每次全量加载** |
| Tool 定义 | ~7.5K | |
| MCP | ~3.7K | |
| Subagent | ~0.9K | |

→ **对策**:常驻规则瘦身为「指针」,完整协议/各阶段 playbook 由 MCP 引擎**按阶段即时下发**(护栏 G7);审计 99 条 Skills 与未用 MCP 改为按需加载。

## 四、实现期文件内容撑爆上下文

最大的 conversation 条目:`Tool: Write`(整文件,单条 7.9K / 7.1K / 4.4K…)与 `Tool: StrReplace`(19 次,单条 1.5–4.5K),**全部永久驻留**。这是「计划 + 实现」挤在同一 session 时上下文冲到 90K+ 的直接原因。

→ **对策**:计划与实现**分 session**(G5);实现期优先**精准 StrReplace** 而非整文件 Write;每步进度写 `progress.md` 而非长对话。

## 五、Agent Loop 如何对症

| 病根 | 护栏/机制 |
|---|---|
| 探索占 64%、反复读 | G1 先定位后读 / G2 不重读 / G3 批量并行 / G6 探索预算 |
| conversation 撑到 90K+ | G4 工作记忆落盘 `.agent-loop/` / G5 计划与实现分 session |
| 固定开销 34K 常驻 | G7 常驻瘦身 + 引擎按阶段 JIT 下发 playbook |
| 流程不稳 | 六阶段 + 闸门(未澄清不调研、未获批不实现、无证据不算完) |

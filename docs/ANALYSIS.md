# Session 优化分析(本引擎的证据基础)

数据来源:自建工具「Cursor Context Usage」(`http://localhost:4173/`,API `/api/sessions`、`/api/stats`)导出的真实开发 session。

> **更新(2026-06-22):样本从 6 → 16 个 session。** 结论:核心论点(探索类调用占大头)在 2.7 倍样本上**被证实、未被推翻**;更大的样本另外暴露了一个 6-session 看不到的现象 —— **任务双峰分布**,据此对「入口分流」做了一处细化(见第六节)。原 6-session 数字保留在第二节作对照。

## 一、16 个 session 仍是同一套工作流(+ 新增小任务)

聚合:`sessionCount=16`,`avgTokensUsed≈79K`(6-session 时 95.8K),`avgPercentFull≈39%`(原 48%)。均值下降主要因新样本含大量小任务,**不是**大任务变省了——最大的需求 session 反而创了新高(166 calls / 115K conv)。

共同骨架未变:**录入需求 → 澄清 → 调研 → 计划 → 实现 → 验证**(部分需求来自原型/PRD 链接)。

## 二、最大浪费:探索类调用占比(16 个 vs 原 6 个)

| 样本 | 总工具调用 | 探索(Read/Grep/Glob/语义)占比 | 平均 conversation |
|---|---|---|---|
| 新 10 个 | 467 | **68%** | 36.7K |
| 原 6 个 | 492 | 65% | 61.4K |
| **全部 16 个** | **959** | **67%** | 46.0K |

- **结论稳定**:无论新老,探索类调用都占 ~2/3,是头号成本;**Grep 在新 session 里更突出**(多个 session Grep>Read,如 Grep 24/21/17)。
- 极端样本:`API sorting order` 96% 探索、`profile_snapshot` 100%、`Product filter bug` 89%(46 调用却只有 2 次改动)。
- 每条 Read/Grep 结果仍**永久驻留对话**,conversation 仍是单 session 最大开销区。

→ **对策(不变)**:INVESTIGATE「先定位后精读、同一文件不重读、发现落盘 context-map、设探索预算」(G1/G2/G3/G6)。

## 三、固定开销每 session ~33K(基本不变)

| 类别 | 每 session 均值(16) | 6-session 时 |
|---|---|---|
| Rules | ~11.4K | ~11.6K |
| Skills | ~7.6K | ~10K |
| Tool 定义 | ~8.4K | ~7.5K |
| MCP | ~4.0K | ~3.7K |
| Subagent | ~1.0K | ~0.9K |
| System | ~0.5K | ~0.5K |

Rules 仍是最大固定块(每个 session 首条都是常驻的 `codegraph.mdc` / `warren-guidelines.mdc`)。→ **对策(不变)**:常驻规则瘦身为「指针」,完整协议/各阶段 playbook 由引擎按阶段 JIT 下发(G7)。

## 四、实现期文件内容撑爆上下文(不变)

大需求 session(如 6060e2c9:166 调用 / StrReplace 39 / conv 115K)仍因「计划 + 实现」同会话、整文件 `Write`/大 `StrReplace` 永久驻留而把上下文顶到 100K+。→ **对策(不变)**:计划与实现**分上下文**(G5,经 `loop_resume` 或 subagent);精准 StrReplace 优先;进度写 `progress.md`。

## 五、Agent Loop 如何对症

| 病根 | 护栏/机制 |
|---|---|
| 探索占 ~67%、反复读 | G1 先定位后读 / G2 不重读 / G3 批量并行 / G6 探索预算 |
| conversation 撑到 100K+ | G4 工作记忆落盘 `.agent-loop/` / G5 计划与实现分上下文 |
| 固定开销 ~33K 常驻 | G7 常驻瘦身 + 引擎按阶段 JIT 下发 playbook |
| 流程不稳 | 六阶段 + 闸门(未澄清不调研、未获批不实现、无证据不算完) |

## 六、新发现:任务双峰分布 → 入口需「分流」(本次唯一行为改动)

16 个样本明显分成两簇:

| 簇 | 代表 session | 特征 | 循环是否划算 |
|---|---|---|---|
| **大需求 / 调研型 bug 排查** | 6060e2c9(166/115K)、5cf57aa8(89/86K)、Product filter bug(46/89% 探索/2 改动) | 多文件调研 + 实质改动;探索量巨大 | **划算**:调研型 bug 排查正是循环最省 token 处 |
| **纯查询 / 小调整** | `Sql extraction`(6/0 改动)、`profile_snapshot`(5/0 改动)、`Binding records sorting`(9/1 改动) | 5–30 次调用、近乎纯探索、~0 改动 | **不划算**:套完整六阶段是净负担 |

原入口规则只区分「非平凡(需求/bug/重构)」与「平凡单行改动」,**没覆盖「纯只读查询/问答」这一类**(约占新样本四成)。

→ **细化(本次改动)**:在协议与各 Agent 入口规则加一句**三路分流** —— 纯查询/问答直接答、平凡单点改动直接改(都不进循环),需求实现/bug 排查/重构才进循环;并给出「5–10 次调用能答完就别套循环」的阈值经验。**这是细化,不是重写**:循环的核心机制(G1–G7、六阶段、闸门、`loop_resume`)经更大样本验证有效,无需改动引擎代码。
